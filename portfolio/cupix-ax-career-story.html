Chapter 01 · 2025.03 – 현재

문제 #1 — 병원은 매번 사람이 전화를 걸어 예약을 확인했다

병원 전화 업무의 상당수는 비슷한 질문의 반복입니다. 예약을 확인하고, 진료 시간을 안내하고, 오지 않을 환자를 다시 붙잡는 일. 와이즈에이아이에서 제가 맡은 첫 과제는 이 반복을 사람이 아니라 시스템이 대신하게 만드는 것이었습니다. 병원이 환자에게 먼저 전화를 걸어 예약을 확인하는 아웃바운드 통화를, 1인으로 설계·개발·운영했습니다.

Before

사람이 반복해서 전화를 건다

  • 상담 인력이 예약 확인 전화를 직접 발신한다
  • 응답이 없으면 재발신도 사람이 판단해서 반복한다
  • 야간·주말에는 기본적인 안내조차 어렵다
After

역할이 분리된 Agent가 통화를 처리한다

  • TriageCoordinator가 의도를 먼저 분류해 라우팅한다
  • BookingAgent·InfoAgent가 예약과 안내를 나눠 처리한다
  • OpenAI Realtime API 단일 파이프라인으로 실시간 대화를 만든다
Design

단일 Agent의 한계에서 Multi-Agent로

처음에는 하나의 Agent로 모든 걸 처리하려 했습니다. 프롬프트가 200줄을 넘고 도구가 14개가 되자 잘못된 도구를 호출하는 빈도가 늘었습니다. 역할별로 Agent를 쪼개 TriageCoordinator(40줄·3개 도구), BookingAgent(50줄·5개 도구), InfoAgent(40줄·6개 도구)로 분리하자 도구 오호출이 눈에 띄게 줄고, 각 Agent를 독립적으로 수정할 수 있게 됐습니다.

Production

실제 전화망에서 마주친 예외

자동응답기(ARS)는 인사말·버튼 안내·반복 루프 3가지 조건을 모두 충족할 때만 감지해 오탐을 줄였습니다. 사용자가 응답 없이 침묵하면 2회 확인 후 종료하고, 상담원 연결이 필요한 경우에는 병원별 정책에 따라 SIP 전환 또는 희망 예약일 수집으로 분기했습니다.

Chapter 02 · 2025

문제 #2 — 이번엔 환자가 먼저 전화를 걸어왔다

아웃바운드는 병원이 먼저 거는 통화라 시나리오가 비교적 단순했습니다. 인바운드는 다릅니다. 환자가 무엇을 원하는지 모르는 상태에서 대화가 시작되고, 병원마다 원하는 응대 방식도 제각각입니다. 같은 원리를 반대 방향에, 그리고 더 유연하게 적용할 수 있을지가 이번 과제였습니다.

Design

콜 플로우를 코드가 아니라 데이터로

병원마다 DTMF 메뉴로 시작할 수도, 자유대화로 시작할 수도 있습니다. 이 모든 시나리오를 하드코딩하면 병원 수만큼 코드가 늘어납니다. 그래서 콜 플로우 자체를 condition / greeting / agent / action / exit 5가지 노드 타입의 그래프(flow_config)로 표현하고, SupervisorAgent가 이를 순회하도록 설계했습니다.

Design

도구 하나도 병원마다 다르게 동작한다

A 병원은 예약 생성을 AI가 자동 처리하지만, B 병원은 예약 변경을 반드시 상담원이 처리해야 합니다. action_mode_handler 데코레이터로 각 도구가 실행 시점에 auto / transfer / leave_memo 설정을 확인하도록 만들어, 도구 코드를 건드리지 않고도 병원별 운영 정책을 바꿀 수 있게 했습니다.

Operator view

병원 운영자가 직접 바꾸는 응대 흐름

아래는 실제 인바운드 응대 흐름을 구성하는 관리 화면입니다. 운영시간 판별, 인사말, DTMF 메뉴, 에이전트 전환, 상담원 연결과 종료까지 코드 배포 없이 이 화면에서 조합합니다.

Chapter 03 · 2025.03 – 2025.05 (아웃바운드 초기와 병행)

문제 #3 — 전화 흐름만으로는 안 되는 대화가 있었다

병원 고객 상담은 정보 안내와 개인정보 수집, 상담원 연결 준비가 한 대화 안에서 섞여 나옵니다. 단순 FAQ 응답기로는 부족했습니다. 전화 흐름만이 아니라, 지식이 필요한 대화도 시스템으로 다뤄야 했습니다. 핵심 아키텍트로서 LangGraph 기반 상담 구조를 주도했습니다.

State machine

상태를 명시적으로 관리해 절차가 섞인 상담을 안정화

primary_assistant, customer_interaction, extract_personal_info, tools 노드를 분리하고 pending_question, collected_info 같은 상태를 명시적으로 관리했습니다. "상담원 연결해 주세요. 임플란트 상담도 가능한가요?"처럼 요청이 섞여 들어와도, 개인정보를 먼저 수집한 뒤 원래 질문으로 자연스럽게 복귀합니다.

Chapter 04 · 2026

문제 #4 — 일이 자동화되니, 그 일을 들여다보는 일도 반복업무가 됐다

아웃바운드와 인바운드를 합쳐 하루 평균 4,000건에 가까운 통화가 쌓이기 시작하자, 이번엔 "이 통화에서 무슨 일이 있었는가"를 사람이 하나씩 확인하는 일이 새로운 반복 업무가 됐습니다. 실시간 통화와 분석 부하를 분리하면서도, 한 통화의 업무 결과와 품질을 재구성할 수 있는 Kafka 기반 후처리 파이프라인을 구축했습니다.

Diagnosis

결과에서 개선 과제로

대화 transcript, 구조화 Agent event, 녹음과 단계별 latency metric을 Kafka로 전달하고, room_name 기준 멱등 처리가 가능한 Consumer로 분석 장애가 실시간 통화에 영향을 주지 않도록 분리했습니다. 원본 event를 업무별 시도와 통화별 최종 결과로 정규화해, 실패를 단계·유형·개선 주체로 분류합니다.

Kafka 비동기 분리업무 시도 / 최종 결과 정규화실패 원인 분류
Split

결정론적 완료 판정과 LLM 품질 평가를 분리

업무 완료 여부는 결정론적 event로 계산하고, 요청 의도와 응답 품질만 근거 turn을 포함한 LLM 평가로 판단했습니다. task_completion, routing_correctness, response_quality를 버전이 있는 Langfuse session score로 발행해 운영 지표와 품질 지표를 뒤섞지 않았습니다.

Privacy

추세는 보되 개인정보는 남기지 않는다

환자 transcript·식별 정보는 내부 저장소에 유지하고, 비민감 집계값만 Langfuse로 전송했습니다. 통화·점수·평가 버전 기반 idempotency key와 hard-cap 규칙으로 재평가 일관성과 개인정보 경계를 함께 지켰습니다.

Chapter 05 · 2026.08 – 현재 (착수 3주 차)

문제 #5 — 이번엔 병원이 아니라, 우리 팀 자신의 문제였다

운영·HQ/SVC 담당자들은 AIU 제품 사용법, 통화 운영 현황, Agent Admin 설정, 운영 지표를 각기 다른 시스템에서 찾고 있었습니다. 대상은 환자의 전화가 아니라 동료의 질문이었지만, 반복되는 조회 업무라는 형태는 앞의 네 챕터와 똑같았습니다. 그래서 같은 근육을 한 단계 위, 사내 업무지원이라는 새로운 문제에 적용했습니다.

Routing — Chapter 1의 재적용

Supervisor + 4개 도메인 Agent

최상위 Supervisor가 요청 도메인을 판별해 inbound-agent, outbound-agent, agent-admin-agent, hq-svc-agent 네 전문 Agent에 위임합니다. TriageCoordinator가 예약과 안내를 나눴던 것과 같은 원리를, 이번엔 제품·데이터·권한 경계를 나누는 데 썼습니다.

Policy — Chapter 2의 재적용

코드가 아니라 계약으로 권한을 고정

5개 사내 시스템의 사용자·AI 매뉴얼 322개를 Google Cloud OKF v0.2 지식 번들로 통합하고, source manifest와 frontmatter의 역할·claim·분류 정보로 검색 전에 접근 범위를 제한했습니다. flow_config가 병원별 정책을 설정으로 바꿨던 것처럼, 이번엔 역할·claim 계약이 그 자리를 대신합니다.

Guardrails

SELECT-only 데이터, HITL, 감사 로그

통화 검색과 운영 지표 분석을 위한 SELECT-only MySQL Tool은 사용자 입력을 parameter binding으로 분리하고 SSL 인증서를 검증하며, 조회 한도와 transcript 비식별화를 기본값으로 둡니다. 민감 통화는 후보 5건만 읽고 전화번호·주민번호·이메일을 비식별화했습니다. 브라우저·파일·plugin 실행은 정책 평가·감사 로그·Human-in-the-Loop을 거치도록 AG-UI로 Web·Slack 실행을 하나의 runtime에 묶었습니다.

Why Cupix

어떤 반복 업무든, 경계와 예외를 파악해 구조화된 시스템으로 바꾼다

다섯 챕터를 관통하는 패턴은 하나입니다. 대상이 병원 전화든, 사내 매뉴얼 조회든, 반복되는 업무의 경계와 예외를 파악해 구조화된 시스템으로 바꾸는 것. 큐픽스 AX Operations Engineer 공고가 예시로 든 월간 리포트 자동화, 고객 문의 분류, 세일즈 리드 정리는 형태만 다를 뿐, 위에서 다룬 문제들과 같은 모양의 문제라고 생각합니다.

이 저장소에서 보여준 것

병원별로 다른 정책을 flow_config / action_mode_handler로 다룬 경험

부서마다 다른 리포트 형식을 하나의 구조화된 파이프라인으로 통합하는 일 — 월간 리포트 자동화

SELECT-only 지표 조회와 OKF 지식 계약을 설계한 경험

↓ 같은 모양의 문제

흩어진 데이터를 근거 있는 형태로 구조화하는 일 — 세일즈 리드 정리

솔직한 지점

Make·Zapier·n8n 경험은 없습니다

위 다섯 프로젝트 모두 로우코드 자동화 툴이 아니라 백엔드 코드로 직접 설계·구현했습니다. 병원 예약 정책, 사내 문서 접근 권한처럼 도메인별 권한과 데이터 경계가 코드 수준에서 분명해야 하는 업무가 많았고, 그 경우 코드 기반 자동화가 로우코드 툴보다 더 유연하고 견고했기 때문입니다. 로우코드 툴 자체를 다뤄본 적은 없지만, Deep Agents·LangGraph로 더 복잡한 자동화 파이프라인을 직접 설계해 온 만큼 짧은 시간 안에 익힐 수 있는 기반은 갖췄다고 생각합니다.
