Project 01

아웃바운드 Voice AI는 설계 실험이 아니라 운영 제품이었다

예약 확인·안내 전화를 AI가 자동 발신하고, 통화 후 전사 교정·구조화 분석·요약까지 비동기로 이어지는 실시간 시스템을 1인 설계·개발·운영했습니다.

01
Problem

단일 Agent의 한계

200줄이 넘는 프롬프트와 14개 도구를 한 에이전트에 몰아넣자 오호출과 유지보수 문제가 드러났습니다.

Prompt overload Tool confusion
02
Decision

Multi-Agent 분리

TriageCoordinator / BookingAgent / InfoAgent로 역할을 분리하고 사용자 원본 발화를 handoff해 대화를 끊지 않도록 설계했습니다.

Routing Context handoff
03
Result

실서비스 성과

100개+ 병원, 일 2,000건, 누적 96,000건+ 통화를 처리했고 Realtime API로 약 900ms 파이프라인을 약 300ms 수준으로 줄였습니다.

100+ hospitals ~300ms
Metrics

운영 지표가 아웃바운드 시스템의 완성도를 증명합니다

실시간 대화 품질, 도입 규모, 다국어 범위를 동시에 맞췄다는 점이 핵심입니다.

Key Takeaways
  • 실제 전화망 기반 운영을 전제로 한 시스템이었다.
  • 성능 개선은 단순 모델 교체가 아니라 파이프라인 구조 변경의 결과였다.
  • 통화 이후 분석까지 이어지는 비동기 처리로 운영 활용도를 높였다.
Project 02

인바운드는 “전화가 들어왔을 때 무엇을 할지”를 데이터로 다뤘습니다

환자가 먼저 전화를 거는 환경에서는 병원마다 시나리오가 달라지기 때문에, 하드코딩 대신 flow_config 기반 노드 그래프로 콜 플로우를 설계했습니다.

Core Design

SupervisorAgent + flow_config

condition

운영시간, 세션 데이터, 정책 기반 분기

greeting

DTMF IVR 또는 자유대화 진입 처리

agent

Booking / Info / Triage 에이전트 전환

action / exit

상담원 연결, 로깅, 통화 종료

Why It Matters
  • 병원별 시나리오를 코드 변경 없이 JSON 설정으로 제어
  • DTMF와 자유대화 플로우를 같은 엔진에서 처리
  • action_mode_handler로 auto / transfer / leave_memo 정책 전환
  • Warm / Cold Transfer, 재시도, fallback을 하나의 제품 흐름으로 정리
Project 03

병원 고객상담 AI는 답변보다 상태 설계가 중요하다는 점을 보여줍니다

일반 문의, 개인정보 수집, 상담원 연결 준비가 한 대화에 섞이는 상황을 LangGraph 기반 상태 모델로 분리해 상담 시스템으로 설계했습니다.

State Model

대화 단계를 노드와 상태로 분리

  • primary_assistant: 질문 의도 해석과 일반 응답
  • customer_interaction: 개인정보 수집 및 연결 준비
  • extract_personal_info: 필수 정보 추출·검증
  • tools: 검색과 후속 동작을 별도 책임으로 분리
Service Boundary

에이전트만이 아니라 서비스 전체를 설계

  • Qdrant 기반 병원 지식 조회 구조
  • FastAPI + LangGraph SDK 비동기 API 서버
  • Next.js 운영 대시보드와 모니터링 흐름
  • AWS ECS Fargate 배포 구조로 운영 가능한 제품 경계 수립
Comparison

세 프로젝트는 같은 문제를 다른 수준에서 풀었습니다

아웃바운드는 운영 성과, 인바운드는 설정 기반 확장성, 고객상담 시스템은 상태 기반 아키텍처 설계를 보여줍니다.

Outbound

운영 규모

  • 실시간 전화망 연결
  • 다국어 지원
  • 96,000건+ 누적 성공 통화
Inbound

설정 기반 제어

  • flow_config 노드 그래프
  • Warm / Cold Transfer 설계
  • 정책별 동적 도구 행동 분기
Customer Support

상태 기반 상담

  • 질문 맥락 유지
  • 개인정보 수집 후 복귀
  • 검색·API·대시보드 경계 설계

Principles

제가 반복해서 선택한 기술적 방향

01

역할을 분리해 복잡도를 낮춘다

모델을 더 똑똑하게 만드는 대신, 에이전트와 상태의 책임을 나눠 예측 가능성을 높였습니다.

02

정책은 코드보다 데이터에 둔다

병원별 시나리오 차이는 설정과 노드 그래프로 풀어 제품 확장 비용을 낮췄습니다.

프로토타입이 아니라 운영 구조를 같이 설계한다

분석 큐, 오토스케일링, 구조화 로그, 환경 분리까지 초기에 포함해 실제 서비스로 연결했습니다.
