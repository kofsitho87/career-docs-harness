Why this work

문제는 모델이 아니라 찾는 비용이었다

제품 화면, 운영 콘솔, 매뉴얼, DB 조회가 시스템마다 달랐습니다. 같은 질문을 해도 사람마다 다른 화면을 열고, 지표 정의가 어긋날 수 있었습니다. 이 과제는 새 Agent를 자랑하는 일이 아니라 그 반복을 줄이는 일이었습니다.

Before

제품별 화면을 외운다

  • AIU 사용법은 매뉴얼 저장소에서 찾는다
  • 통화 운영 현황은 인바운드·아웃바운드 콘솔이 다르다
  • 설정 변경 위치는 Agent Admin 화면 경로에 의존한다
  • HQ/SVC 정책은 또 다른 문서 묶음에 있다
After

업무 언어로 한 곳에서 묻는다

  • Web과 Slack이 같은 AG-UI 런타임을 쓴다
  • Supervisor가 도메인을 나누고 허용된 Agent만 답한다
  • 문서는 역할·claim을 통과한 뒤에만 본문을 연다
  • 운영 지표는 SELECT-only로, 같은 계산 규칙을 코드에 둔다
What people can ask

현업이 실제로 던지는 질문 형태

도메인마다 문서·Tool·응답 계약이 다릅니다. 아래는 실제 운영 데이터 수치가 아니라, Agent가 처리하도록 설계한 질문 유형입니다.

Inbound Agent

운영 현황을 콘솔 경로 없이 묻는다

이번 주 인바운드 응대율과 예약 전환율을 비교해 줘. 이탈이 인사말 전에 몰리는지도 같이 봐줘.

허용된 역할이면 SELECT-only Tool이 날짜·병원·업무 결과 필터로 집계합니다. 지표 정의는 화면마다 달라지지 않도록 코드로 고정했습니다. 민감 통화 원문은 후보 제한과 비식별화를 거친 뒤에만 봅니다.

How it runs

질문에서 실행 가능한 업무까지

기존 AIU Agent를 Bun·TypeScript 기반 Deep Agents로 옮기고, AG-UI로 Web과 Slack 실행을 하나의 런타임에 묶었습니다. 노드를 누르면 그 레이어가 왜 필요한지 볼 수 있습니다.

Entry

하나의 업무 접점

현업은 제품별 화면과 데이터 저장소를 외우지 않습니다. Web 또는 Slack에서 업무 언어로 질문하면 같은 Agent runtime이 응답합니다.

Knowledge contract

문서를 모으는 것이 아니라
접근 계약을 만든다

5개 사내 시스템의 사용자 매뉴얼과 AI Playbook 322개를 Google Cloud OKF 지식 번들로 통합했습니다. RAG를 붙이기 전에, 누가 어떤 본문을 열 수 있는지를 frontmatter 계약으로 고정했습니다.

Bundle

한 형식, 두 독자

사람용 매뉴얼과 Agent용 Playbook·Policy·State Model을 같은 번들로 둡니다. 설명이 갈라지면 운영과 AI 응답이 동시에 어긋납니다.

Pre-retrieval

본문 전에 권한을 줄인다

역할·claim·문서 분류로 검색 범위를 먼저 자릅니다. Supervisor는 원본 문서를 직접 읽지 못하고, 해당 도메인 Agent만 허용된 지식을 봅니다.

Integrity

문서와 코드를 같이 검사한다

source drift, 깨진 링크, capability coverage, HITL 정책을 deterministic checker와 테스트로 확인합니다. 문서 본문은 사람 검토 중인 draft로 관리합니다.

Internal ops surface

찾아 들어가던 화면을
질문으로 바꾼 근거

아래는 인바운드 운영 콘솔 샘플입니다. Agent는 이 화면의 메뉴 경로를 외우게 하지 않고, 같은 운영 정의로 자연어 조회에 응답합니다. 숫자는 비식별 샘플이며 실제 운영값이 아닙니다.

01 · Operating status

운영 지표를 업무 언어로

응대율, 자체 처리율, 예약 전환율, 상담원 연결 성공률을 화면마다 다시 세지 않습니다. 날짜·병원·업무 결과 필터와 계산 규칙을 SELECT-only Tool에 명시했습니다.

자연어 조회지표 정의 고정콘솔 경로 제거
02 · Diagnosis

결과에서 개선 과제로

대화와 Tool event를 업무 시도와 최종 결과로 재구성합니다. 자체 처리로 끝난 통화와 상담원 연결·이탈을 같은 기준으로 나눠, 운영자가 다음 조치를 누가 맡아야 하는지 보게 합니다.

업무 시도 / 최종 결과실패 원인 분류재처리 가능
Guardrails

AI가 일하려면 경계부터 설계한다

사내 데이터와 고객·환자 식별정보가 섞일 수 있는 업무라서, 도구를 여는 속도보다 열리지 않아야 할 경로를 먼저 막았습니다.

Access

Role · Claim 사전 필터

인증된 역할과 claim으로 본문 로드 전 문서 집합을 줄입니다. 검색이 먼저 되고 권한이 나중에 붙는 구조를 피했습니다.

Data

SELECT-only 조회

사용자 입력은 parameter binding으로 분리하고 SSL을 검증합니다. 조회 한도와 raw transcript 비노출을 기본값으로 둡니다.

Privacy

식별정보 비식별화

민감 통화 검토는 최대 5건의 명시적 후보만 읽습니다. 전화번호, 주민번호, 이메일을 가리고 원문 전체 덤프를 막습니다.

Execution

HITL · 감사 로그

서명된 사용자 실행 정보만 Agent가 수락합니다. 브라우저·파일·plugin 작업은 정책 평가와 사람 승인을 통과해야 합니다.

Stack & verification

이 프로젝트를 구분하는 기술

LLM API나 MySQL, Slack은 연동 대상입니다. 이 과제의 핵심은 Agent 런타임, 채널 프로토콜, 지식 계약입니다.

TypeScriptBunDeep AgentsAG-UIGoogle Cloud OKF
37개 자동화 테스트가 지키는 것
  • 지식 manifest와 역할·claim 격리
  • AG-UI 응답 계약
  • DB 조회 한도와 SELECT-only 경계

연동은 보이되 기술 줄에는 넣지 않은 것

OpenAI API, MySQL, Slack, Docker Compose는 실제로 붙였습니다. 다만 이 프로젝트를 다른 Agent 작업과 구분하는 키워드는 아니라서 핵심 스택에서 뺐습니다.
