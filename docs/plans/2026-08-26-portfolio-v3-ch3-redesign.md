- 이 챕터는 이전 챕터의 전화 Voice AI가 아니라 **웹·Kakao에서 사용하는 챗봇 인터페이스**다. SIP·음성 처리 대신 화면의 입력창·응답 카드·버튼을 통해 상담한다는 차이를 첫 두 장에서 바로 보여준다.
- 이 챕터의 핵심은 기능 목록이 아니라 **병원별 지식 조회, 개인정보 수집, 예약 안내와 상담원 연결 준비가 하나의 대화 상태를 공유하도록 만든 상담 구조**다.
- 기존 3장은 소개, 다섯 게이트, 결과와 한계만 보여줘 전체 시스템 아키텍처·병원별 지식 검색·서비스 실행 경계가 충분히 드러나지 않는다.
- 5장 구성을 확정해 사용한다. 현재 CH 03은 5장, 전체 덱은 29장이며 CH 04는 24에서 시작한다.
- 흐름은 `챗봇 프로젝트 소개 → 실제 챗봇 인터페이스에서 시작하는 시스템 아키텍처와 기술 스택 → 상태 기반 상담 → 병원별 지식 응답 → 운영 가능한 서비스 경계와 배운 점`으로 전개한다.
- CH 01의 전화 Voice AI와 역할을 분리한다. 이 챕터는 웹·Kakao 등 텍스트 채널에서 병원 상담 절차와 상태를 어떻게 제품 구조로 만들었는지에 집중한다.
- CH 02의 사후 통화 분석과도 역할을 분리한다. 이 챕터는 상담이 진행되는 동안 질문 맥락과 절차 상태를 유지하는 런타임 설계가 중심이다.
- 프로젝트 기간은 사실 기준 문서에 따라 `2025.03 – 2026.03`으로 사용한다.
- 역할은 `초기 상담 그래프와 서비스 경계 설계·주요 구현`으로 표현한다. 이후 팀이 추가한 Harness·Kakao 확장을 본인 구현처럼 설명하지 않는다.
- 최신 Harness 구조는 초기 상태 모델이 확장을 수용한 근거로만 다루고, 현재 기능 전체를 본인의 성과처럼 나열하지 않는다.
- 예약은 직접 실행하지 않고 요청 의도에 맞는 UI를 여는 범위다. 의학적 판단도 수행하지 않는다.
- 정량 성과를 새로 만들지 않는다. 설계 난이도, 상태 복귀, 병원별 데이터 격리, 실행 가능한 서비스 경계를 구현 증거로 사용한다.
- 기술 용어는 쉬운 설명 다음에만 작게 표시한다. `pending_question`, `collected_info`, `Dense+Sparse Hybrid Search`, `LangGraph SDK`는 구현 근거로만 사용한다.
- 모든 장에는 아이콘, 상태 흐름, 아키텍처, 검색 단계, 실제 화면 중 메시지에 맞는 시각 요소를 최소 하나 사용한다.
- 기존 챕터 2와 같은 크기 기준을 적용한다. 1920×1080에서 제목·본문·아이콘·스크린샷이 작아 보이지 않게 구성한다.
- 실제 상담 화면을 사용할 때는 환자 이름·전화번호·생년월일·병원 식별정보를 확인하고, 필요하면 비식별 자르기 또는 마스킹 후 사용한다.
- 실제 화면은 장의 핵심을 설명하는 증거로만 사용하고, 스크린샷만으로 한 장을 채우지 않는다.

## 챕터 핵심 메시지

> 병원 상담을 단순 질문 답변이 아니라, 지식 조회와 개인정보 수집을 거친 뒤에도 원래 질문으로 돌아오는 상태 기반 제품으로 설계했습니다.

이 메시지를 아래 세 가지 증거로 뒷받침한다.

1. **대화 상태**: 일반 문의 도중 개인정보 수집이 끼어들어도 원래 질문과 이미 수집한 값을 보존한다.
2. **병원별 근거**: 기관·운영시간·의료진·진료·시술·증명서·이벤트 정보를 병원별 Fact Data와 검색 Tool로 조회한다.
3. **제품 경계**: 상담 그래프만 만들지 않고 FastAPI gateway, LangGraph thread·run, PostgreSQL·Redis, 지식 검색과 Docker 실행 경계를 함께 구성한다.
