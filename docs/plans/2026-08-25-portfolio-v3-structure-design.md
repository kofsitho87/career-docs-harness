## 문제 정의

v2는 다섯 챕터가 모두 같은 틀을 쓴다. `Background → Process → Outcome → My Role` + `Problem State → Designed System`.

이 틀은 이력서 문법이다. "내가 무엇을 했는가"에는 답하지만 "이 시스템이 무엇인가"에는 답하지 않는다. 네 가지 결과가 나온다.

1. **시스템 정의가 없다.** CH02 인바운드는 첫 문장이 "운영시간·DTMF·예약·병원 정보·상담원 연결이 한 통화에 섞입니다"다. 이미 시스템을 아는 사람의 언어이며, 환자가 전화를 걸었을 때 무슨 일이 벌어지는지를 네 장 내내 보여주지 않는다. CH01이 무사한 것은 "직원이 전화를 건다"가 설명 없이도 그려지기 때문이지 틀이 좋아서가 아니다.
2. **결론만 있고 사건이 없다.** "네 가지 안전 불변식", "ZSET/HASH/STREAM 역할 분리"는 판단의 결론이지 근거가 아니다. 독자는 왜 그렇게까지 해야 했는지 모른다.
3. **종속 관계가 보이지 않는다.** CH04 통화 관측·평가는 CH01/CH02가 만든 통화를 분석하는 층인데, 다섯 챕터가 평평하게 나열돼 독립 프로젝트로 읽힌다.
4. **분량과 내용량이 반대다.** CH01은 7장, CH02는 4장이다. CH02가 담은 내용이 더 적지 않다.

## 중심 원칙

### 1. 그림이 먼저, 기술이 다음

시스템 설명은 문단이 아니라 경계도 한 장과 정의 세 줄로 끝낸다. 독자가 머릿속에 상자 하나를 그린 뒤에야 그 안의 부품을 설명한다.

### 2. 기능마다 사건이 붙는다

기능을 나열하지 않는다. 기능 하나를 `무엇을 하는가 → 어떻게 만들었나 → 뭐가 깨졌나` 세 겹으로 판다. **세 번째 겹이 없는 기능은 슬라이드로 만들지 않는다.** 이 규칙이 기능 소개서로 떨어지는 것을 막는다.

세 번째 겹은 **실제 실패 사례**이거나 **의도적으로 그은 경계**다. 후자는 "할 수 있지만 하지 않기로 한 것"이며, 그렇게 정한 이유가 함께 있어야 한다. 어느 쪽이든 근거 문서에서 나와야 하고 각색하지 않는다.

### 3. 수치는 뒤에, 한계는 명시한다

수치를 앞에 두면 그냥 숫자지만 뒤에 두면 판단들을 거쳐 나온 결과가 된다. 마지막에 못 하는 것을 직접 쓴다. 경계를 스스로 긋는 신호가 수치보다 강하다.

## 정보 구조

챕터 넷, 층 하나. 실제 종속 관계가 있을 때만 묶는다.

```
오프닝 · 나는 어떤 문제를 푸는 사람인가
챕터 지도

1 · 병원 전화 Voice AI     거는 전화 + 받는 전화
2 · 통화 관측과 평가       1의 결과를 받는 층
3 · 챗봇 고객상담
4 · AIU 사내 업무지원

클로징 · 반복되는 방식
```

**인바운드와 아웃바운드를 한 챕터로 합친다.** 두 위키를 대조한 결과 기능과 런타임이 대부분 같다.

| 공통 | 근거 |
|---|---|
| `SingleAgent` + `flow_config` 5종 노드 | 양쪽 위키가 동일한 `condition`/`greeting`/`agent`/`action`/`exit` 구성을 기술 |
| DTMF 액션 매핑 5종 | `booking_create` / `booking_inquiry` / `booking_modify` / `booking_cancel` / `info_look_up` |
| `action_mode_handler` 3종 | `auto` / `transfer` / `leave_memo` |
| `GreetingDtmfTask` | 5초 타임아웃, 무효 2회, replay 키, 세션 presence task 억제 |
| **Warm Transfer 큐 공유** | 아웃바운드 위키가 명시한다. "shares a company FIFO queue between inbound/outbound calls" |
| ZSET/HASH/Stream 구조 | 동일한 키 구성과 660초 TTL, 120/240/360초 대기 재확인 |

따로 설명하면 같은 내용을 두 번 쓰게 된다. v2가 실제로 그랬다.

**관측과 평가는 별도 챕터다.** 두 서비스의 분석 파이프라인이 완전히 분리돼 있음을 위키에서 확인했다.

| | 아웃바운드 | 인바운드 |
|---|---|---|
| 입력 토픽 | `aiu.outbound-call.analysis` | `aiu.inbound-call.analysis` |
| 출력 토픽 | `aiu.outbound.agent-call-analysis-complete` | `aiu.inbound.call-end` |
| 테이블 | `conversation_results`, `conversation_events` | `inbound_conversation_results`, `inbound_call_analytics`, `inbound_call_attempts`, `inbound_call_semantics` |
| 판정 방식 | LLM 분류(Trustcall) 중심, 결정론적 classifier와 shallow-merge | 결정론적 `events → attempts → rollup`, 의미 분석은 격리된 별도 층 |

챕터 1의 결과를 받는 후처리이므로 순서상 바로 뒤에 놓지만, 다룰 판단이 독립적이므로 하위 항목이 아닌 챕터로 둔다.

**단, 두 파이프라인을 비교하는 구성으로 쓰지 않는다.** 인바운드 쪽이 결정론적 귀속·의미 분리·버전 관리·백필까지 갖춰 더 발전한 것은 사실이지만, 그것은 두 위키를 대조해 얻은 해석이지 대화분석 시스템 자체의 기능이 아니다. 챕터 2는 **어떤 과정으로 이루어지고 그걸로 무엇을 하는가**로 전개하며, 성숙도 차이는 필요한 곳에서 한 줄로만 언급한다.

**챗봇 고객상담은 하위가 아니다.** `2025.03 – 2026.03`, 채널이 웹·Voice·Kakao인 멀티채널 상담 제품으로 인/아웃바운드와 병렬 진행됐다. 다만 초기 그래프와 서비스 경계를 만들고 팀에 넘긴 프로젝트이므로 짧게 다룬다.

챕터 번호는 `1`~`4`를 쓰고 하위 번호를 두지 않는다. 계층이 하나뿐이므로 `1-1` 형식이 불필요해졌다.

## 챕터 공통 3단 틀

네 챕터가 모두 같은 3단을 쓴다. 독자가 첫 챕터에서 리듬을 익히면 나머지는 예측하며 읽는다.

| 단 | 내용 | 분량 |
|---|---|---|
| **① 무엇인가** | 짧은 정의 + 흐름 그림 한 장 + 안 하는 것 | 1~2장 |
| **② 기능별로 깊게** | 기능마다 `무엇 → 어떻게 → 뭐가 깨졌나` | 1~6장 |
| **③ 결과와 한계** | 검증 · 수치 · 못 하는 것 | 1장 고정 |

**챕터 분량은 주로 ②의 개수로 달라진다.** ③은 언제나 한 장이다.

**①이 2장이 되는 경우는 하나뿐이다.** 운영 규모가 그 챕터를 읽을 이유 자체일 때, 규모를 ①의 두 번째 장으로 둔다. 규모는 "이 시스템이 무엇인가"의 일부이지 판단의 결과가 아니므로 ②③이 아니라 ①에 속한다. 현재 챕터 1만 해당한다 — 다른 세 챕터는 이 수준의 운영 데이터가 없다.

#### 재설계 이유

초판은 `①1 + ②3 + ③1` 다섯 장이었다. 두 가지가 문제였다.

1. **기능 세 장이 연달아 나와** 독자가 "이 시스템이 사업적으로 무엇을 바꿨나"를 마지막 장까지 알 수 없었다. 성과가 결론에만 있으면 그 앞의 일곱 장을 읽을 이유가 생기지 않는다.
2. **상담원 연결을 큐 이야기부터 시작했다.** 정작 이 기능이 에이전트 구조 어디에 붙어 있는지를 보여주지 않아, 독자는 왜 큐가 필요한지 모른 채 Redis 키 세 개를 읽게 된다.

**한 줄 메시지 작성 규칙.** 슬라이드를 보지 않고 여덟 줄만 이어 읽어도 챕터가 이해되어야 한다. 내부 축약어(`갈라놨다`, `증거가 남는다`, `아직 신청`)를 쓰지 않고, 비유 대신 하는 일을 그대로 적는다. 목차 라벨(`개선 지표와 한계`)은 메시지가 아니다.

#### S1 · ① 무엇인가

핵심은 **직무를 먼저 말하는 것**이다. 초판은 "두 방향에서 대신합니다"로 시작해 시스템 구조를 먼저 꺼냈다.

- 정의: 병원 데스크 직원이 받던 전화를, 걸고 받는 두 방향 모두 24시간 대신한다
- 왜 필요한가: 진료 중이라 못 받는 전화, 마감 후 걸려온 전화, 부재중 후 다시 걸지 않는 환자. 이것이 놓치는 예약이다
- 기능 여섯: 병원 지식 답변 · 신규 예약 신청 · 예약 조회 · 예약 변경 · 예약 취소 · 상담원 연결(실패 시 메모 접수)
- 규모: 6개 언어(`ko-KR`, `en-US`, `zh-CN`, `ja-JP`, `es-ES`, `vi-VN`), action mode 3종(`auto` / `transfer` / `leave_memo`)
- 안 하는 것: EMR 확정이 아님, 병원 근거 없는 답변 안 함(조회 실패 시 no-knowledge 상태로 통화 계속)

**4단계 흐름도는 S3으로 내린다.** 첫 장에 구조도까지 있으면 "무엇인가"가 흐려진다.

기능 여섯 중 **신규 예약만 재설계됐다.** 인바운드 위키가 명시한다. "Inquiry, modification, and cancellation remain legacy tools." 따라서 나머지는 S1에 한 줄씩 놓고 깊게 파지 않는다. 원칙을 지키려고 억지로 뺀 것이 아니라 실제 구현이 그렇다.

#### S2 · ② 운영 성과

**신설.** 규모와 도달을 여기서 말하고, 개선 지표는 S8로 보낸다. 두 수치는 성격이 다르다 — 규모는 판단의 전제이고 개선은 판단의 결과다. 전제는 앞에, 결과는 뒤에 둔다. 중심 원칙 3과 충돌하지 않는다.

| 수치 | 범위 |
|---|---|
| 누적 620,000+ 통화 · 일 평균 4,000건 · 병원 300+ · 6개 언어 | 양방향 |
| AI가 사람 없이 끝낸 통화 5,056건 · 응대 시간 146.44시간 | 인바운드 |
| 상담원이 받지 못한 용건 12,074건이 메모로 접수 (성사율 71.40%) | 인바운드 |
| 활성 병원 130곳 · 월간 활동 유지율 91.14% | 인바운드 |

**범위 라벨을 반드시 붙인다.** 양방향 수치와 인바운드 전용 수치가 한 장에 섞이므로, 라벨 없이 두면 전부 양방향으로 읽힌다.

**필수 각주.** 146.44시간은 AI가 수행한 응대 시간이지 절감된 인건비가 아니다. KPI 원문이 수동 처리 시간·후처리 데이터가 없어 계산 불가라고 명시한다. 이 한 줄이 나머지 수치의 신뢰를 만든다.

도입 병원 수는 **300+로 유지한다.** AiU 플랫폼 페이지는 705개 병·의원을 표기하지만 그 수치의 범위(전 제품 합산인지 Voice AI 단독인지)가 확인되지 않았다. 확인 전까지 사실 기준 문서(`resume/product-engineer.md:46`)를 따른다.

#### S3 · ② 구조와 스택

- **통화 4단계** (S1에서 내려옴): 병원마다 다른 규칙을 통화 시작 때 받는다 → 그 설정대로 대화를 진행한다 → AI가 처리할지·사람에게 넘길지·메모로 받을지 정한다 → 통화가 끝나면 결과를 분석으로 넘긴다. 민감한 내용은 네 단계 전체를 관통해 밖으로 나가지 않는다
- **두 방향의 시작 차이**

| | 아웃바운드 | 인바운드 |
|---|---|---|
| 시작 | voxBridge가 SIP 참가자를 만들고 **워커는 기다린다** | SIP 수신 후 참가자 admission |
| 게이트 | `FakeAgent` → `sip.callStatus=active`(60초) → **AMD** → human/uncertain일 때만 `SingleAgent` | 유효한 metadata와 참가자 확인 |
| 지식 | FAQ 벌크 프롬프트 주입(`get_faqs`) | Call Context 주입 + no-knowledge fallback |
| 목적 | 발신 시점에 이미 정해져 있다 | 통화 중에 알아내야 한다 |

- **스택**: Self-hosted LiveKit · LiveKit Agents · SIP Trunk / AWS Streaming STT · GPT-5.4-mini · Gemini 2.5 Flash Lite · Google TTS / Redis · MySQL · Kafka. **배포 인프라(ECS Fargate, Kubernetes 리전 구성)는 넣지 않는다** — 이 챕터의 주장에 기여하지 않는다
- **핵심 판단 한 줄**: 실시간 통화와 분석을 Kafka로 끊어 분석 장애가 통화를 죽이지 않게 했다. 챕터 2로 넘어가는 다리다
- **동시성 상한**: `compute_load()`가 활성 잡 5개를 기준으로 계산해 연결 5통 + 셋업 1건까지 허용하고 7번째를 막는다

깨진 것 둘을 넣는다. 둘 다 **통화 초기 상태 오염** 문제로 묶인다.

1. **AMD 판별 중 시작된 발화가 Agent 전환 후 완료되어 설정 인사말 대신 LLM 응답이 나가던 race condition.** 발화가 금지된 `FakeAgent`와 `GreetingDtmfTask`에서 `StopResponse`를 강제해 결정적 인사말 경계를 지켰다.
2. **일회성 키패드 선택이 이후 자율 도구 호출로 새는 문제.** `get_my_appointment_list`가 시작 시 `from_dtmf_selection`을 먼저 지운다.

초판 S4의 세 번째 사건(**늦게 도착한 STT 완료가 통화 종료 후 발화처럼 보이던 문제**)은 분석 단계에서 `PARTICIPANT_DISCONNECTED`를 끝으로 이동시켜 해결한 것이므로 **챕터 2의 주제다.** 챕터 2 구성 검토 시 편입 여부를 결정한다.

#### S4 · ② 신규 예약

초판 S2를 유지한다.

| 겹 | 내용 |
|---|---|
| 무엇 | 통화 중 예약 신청 접수 |
| 어떻게 | `search → stage → commit`. 확인 문구는 오직 `stage_booking`이 생성하며 모델이 만든 시간은 쓰지 않는다 |
| 깨진 것 | "네" 같은 수긍을 검색 조건으로 착각해 날짜를 지어냄 · 소진돼야 할 `EarliestOffer`가 stale 승인으로 재사용 · 빈 검색 결과에 다른 시간을 몰래 대체 |
| 잡는 법 | 예방은 stage-before-commit, 탐지는 `UNSOUND_COMMIT`. 통화에서 한 번도 발화되지 않은 시간이 커밋되면 성공을 강등하며, 끊긴 assistant 발화는 증거로 인정하지 않는다. 관측 발동률 18건 / 24,647 예약 시도 = 0.073% |

예방과 사후 탐지를 짝으로 만든 것이 이 슬라이드의 핵심이다.

**두 방향의 성숙도 차이를 정직하게 적는다.** 위 내용은 인바운드의 Dynamic Booking v3다. 아웃바운드는 레거시 create 경로가 활성이고 `create_reservation()`을 호출하지 않은 채 신청 정보를 staging한다. 아웃바운드가 같은 수준으로 구현돼 있다고 서술하면 사실과 다르다.

#### S5 · ② 연결 구조

**신설.** 위키에서 확인한 사실이 이 장의 근거다 — **상담원 연결은 독립 기능이 아니라 예약 기능들 위에 얹힌 정책 계층이다.** 예약 도구가 호출되면 실제 처리 전에 `action_mode_handler`가 설정된 모드로 갈라낸다.

시각화가 이 장의 본체다.

```
예약 도구 호출
      │
   action_mode ─┬─ auto ────────▶ AI가 통화 안에서 처리
                ├─ leave_memo ──▶ 메모 접수 후 종료
                └─ transfer
                      │
                 transfer_mode ─┬─ cold ──▶ 즉시 넘기고 빠짐
                                └─ warm ──▶ 대기 → 브리핑 → 연결
```

붙는 사실 셋.

- **연결 번호가 없으면 모드와 무관하게 메모로 간다.** 설정이 무엇이든 마지막은 메모다
- **병원이 직접 지정할 수 있는 것은 신규 예약과 조회뿐이다.** 변경·취소의 모드는 `transfer_mode`에서 파생되며, 설정에 `auto`를 적어도 그렇게 동작하지 않는다
- **경계**: 통화 중 예약 변경·취소는 예약 상태를 바꾸지 않는다. 요청을 전달할 뿐이라 "변경해 드렸습니다"는 사실과 다르다

세 번째가 초판 S5(결론)의 한계 중 하나와 같은 사실이다. **여기가 제자리다** — 구조에서 왜 그런지가 바로 보인다. S8의 한계에서는 뺀다.

**새 CSS 컴포넌트가 필요하다.** 기존 `.flow`·`.states`는 일직선이라 분기를 그릴 수 없다. 이미지 대신 CSS로 만든다 — 덱의 다른 도식이 전부 CSS라 이미지 하나만 섞이면 톤이 어긋나고, 다크·라이트 자동 대응과 텍스트 검색을 잃는다.

#### S6 · ② cold와 warm

**신설.** 두 방식이 **속도와 검증 가능성을 맞바꾼다**는 것이 이 장의 결론이다.

| | cold transfer | warm transfer |
|---|---|---|
| 동작 | 즉시 넘기고 에이전트는 빠짐 | 상담원 응답을 기다려 통화 요약을 전달하고 연결 |
| 대기 | 없음 | Redis FIFO 대기열 + trunk 가용성 폴링 |
| 브리핑 | 없음 | AI가 상담원에게 요약 전달 |
| 재시도 | SIP 403 시 1초 간격 3회 | dial 실패 시 쿨다운 후 재시도 |
| 결과 상태 | `SUCCESS` · `ERROR` | `STARTED` · `SUCCESS` · `FAILED` · `CALLER_DISCONNECTED` · `WAIT_RECONFIRMATION_TERMINATED` |
| 실패 후 | 사과 응답 | **메모 접수로 fallback** |
| 성사 검증 | **불가 — SIP 요청까지만 확인** | 가능 — 브리핑까지 기록 |

- 유형은 넷이다 — `COLD` · `DIRECT_COLD` · `WARM` · `DIRECT_WARM`. 직접 연결 노드는 확인 단계 없이 지정된 대상으로 바로 연결한다
- 연결 직전 의사 확인이 기본이며, 키패드로 직접 선택했거나 이미 `transfer` 경로로 들어왔으면 생략한다
- 대기가 길어지면 120·240·360초에 계속 기다릴지 재확인한다
- 실측: cold 15,798건은 성사로 세지 않는다. warm은 2,899건 중 513건 연결(17.70%)

**cold를 성공에서 제외하는 근거를 명시한다.** 위키가 기록한다 — cold는 LiveKit SIP transfer 요청 후 성공/실패를 별도 상태로 갱신하지 않아 `requested`가 최종 저장값으로 남을 수 있다. 그래서 챕터 2의 분석 파이프라인도 cold를 성사 집계에서 제외한다. 두 챕터가 같은 근거를 공유한다.

#### S7 · ② 대기열

초판 S3의 Redis 내용이 여기로 온다. 도식 `assets/inbound-warm-transfer-flow.png`도 이 장에 붙인다.

두 방향이 **하나의 병원별 FIFO 큐를 실제로 공유**한다. 아웃바운드 위키가 명시한다. "shares a company FIFO queue between inbound/outbound calls."

- **키 3종**: `ZSET` 권위 있는 순서 / `HASH` 대시보드 읽기 모델 / `Stream` 알림 전용(PII 없음). 세 키 모두 `{company_id}`를 포함해 같은 Redis Cluster 슬롯에 둔다
- **불변식 둘**: `enqueue`는 `ZADD NX`를 써서 재큐잉이 원래 순번을 바꾸거나 TTL을 갱신하지 못하게 한다. `cleanup_stale_front`는 ZSET 점수가 오래됐고 **동시에** 메타데이터 HASH가 만료됐을 때만 앞단을 제거한다 — 나이만 보면 아직 갱신 중인 살아있는 통화를 끊는다
- **깨진 것 넷**: 재시도가 큐를 새치기하고 좀비 엔트리를 연장 · 늦게 도착한 콜백이 해제된 HASH를 되살림 · 보관된 완료 기록이 활성 통화로 집계 · "오래됐다"만으로 정리하면 갱신 중인 살아있는 통화를 끊음
- **watchdog 경합**: 전체 무응답 감시 타이머가 DTMF·전환 태스크의 자체 타임아웃과 경합하며, `suppress_user_presence_task`가 해법이다

#### S8 · ③ 결론

- **개선 지표 2개**: 예약 신청·변경·취소·조회를 합친 전체 시도 성사율 8.48% → 25.08%(2026-05 → 2026-08 MTD, +16.6%p), 백엔드 귀인 실패율 8.54% → 0.34%(−8.2%p). **각주 필수** — 2026-04~08 prod 관측이며 활성 고객 구성이 달라져 월별 변화를 제품 성능 변화로 귀속할 수 없다
- **검증 4단계 · 양방향 공통**: 단위 테스트 → LiveKit text-only Agent 평가 → 로컬 환자 시뮬레이션 → 오디오·실제 전화망. 뒤로 갈수록 느리고 현실에 가까우며, 앞 단계에서 걸리는 것을 뒤로 넘기지 않는다. 위키는 코드 근거 문서라 이 체계를 다루지 않으므로 근거는 `resume/product-engineer.md`다
- **한계 2**
  1. 통화 안의 커밋은 예약 *신청* 기록이며 EMR 최종 확정이 아니다
  2. 아웃바운드의 예약 변경·취소는 AI가 실행하지 않는다. 정책에 따라 상담원 연결 또는 메모 접수로 넘긴다

두 번째 한계는 S5에서 구조로 이미 설명했으므로, 여기서는 **결과로 한 줄만** 반복한다. 설명을 다시 하지 않는다.

초판에 있던 "후처리 전달이 원자적이지 않다"는 챕터 2의 ③ 한계와 문장이 동일해 2026-08-25 구현 중 삭제했다. 분석 파이프라인의 속성이므로 챕터 2에만 남긴다.

### 2 · 통화 관측과 평가 (확정)

챕터의 축은 두 개다. **어떤 과정으로 이루어지는가**(S1~S4)와 **그걸로 무엇을 하는가**(S5). 두 프로젝트를 비교하는 구성은 폐기했다. 대화분석 자체의 기능이 아니라 해석이었기 때문이다.

**S1 · ① 대화분석이란 무엇인가**

- 정의: 통화 수천 건의 결과와 품질을, 사람이 녹취를 다시 듣지 않고 재구성하는 후처리
- 왜 분리돼 있나: 실시간 통화 경로와 분석 부하를 Kafka로 분리했다. 분석이 멈춰도 통화는 계속된다
- 파이프라인 그림 한 장: `입력 → 중복 확인 → 정규화 → 전사 보완 → 요약 → 발행 → 저장 → 결정론적 분석 → 의미 분석 → 점수`
- 안 하는 것: 통화 중에는 아무것도 바꾸지 않는다. 전부 사후 처리다

**S2 · ② 과정 하나 — AI가 못 들은 구간을 복원한다**

| 겹 | 내용 |
|---|---|
| 무엇 | 상담원에게 연결된 뒤로는 AI가 대화에서 빠져 있어 통화 기록이 끊긴다 |
| 어떻게 | 녹음을 CloudFront에서 가져와 전환 성공 이벤트 기준으로 크롭하고, Gemini 구조화 출력으로 발신자·상담원 turn을 복원한 뒤 원본 배열 순서를 보존하며 병합 |
| 깨진 것 | 녹음 앵커가 통화 시작과 어긋나 재생 위치가 밀림 · 너무 짧거나 진폭이 낮은 오디오가 잡음을 만듦 · 녹음이 아직 준비되지 않음(가용성 재시도로 대응) |

`recording_started_at`을 기준 앵커로 삼고 없을 때만 최초 assistant 발화로 폴백한다는 점을 명시한다. 시간 기준점 하나가 전사·재생·분석 전체의 정합성을 좌우한다.

**S3 · ② 과정 둘 — 통화 한 건이 어떻게 끝났는지 판정한다**

| 겹 | 내용 |
|---|---|
| 무엇 | 결과와 실패 책임을 LLM 없이 규칙으로 판정 |
| 어떻게 | `events → attempts → rollup` 3층. 통화당 resolution은 정확히 하나이며 7단계 우선순위가 고정돼 있다. 실패는 단계·유형·책임 주체 3요소로 귀속 |
| 깨진 것 | 공유된 transfer 이벤트가 **이전 모든 intent에 중복 청구**됨 · **시스템 종료를 고객 이탈로 오독** · 없는 `result_count`를 0으로 취급 · 생년월일 입력 후 실패와 입력 자체가 없던 실패를 같게 처리 |

배타적 resolution이 KPI 중복 집계를 막는다는 점을 명시한다. 화면의 "통화 결과 분포"가 이 규칙의 직접적인 산출물이다.

**S4 · ② 과정 셋 — 품질을 평가하되 판정은 건드리지 않는다**

| 겹 | 내용 |
|---|---|
| 무엇 | 임상·긴급도·행정·경험·미지원 요청·응답 품질을 LLM으로 평가 |
| 어떻게 | 모든 소견에 신뢰도와 근거 turn index를 요구하고, sanitizer가 날조되거나 범위를 벗어난 증거를 거부. 결정론 계층과 완전히 분리 |
| 깨진 것 | **assistant 발화가 발신자 의도의 증거로 쓰이던 문제** · 단순 가용성 질문을 예약 의도로 오분류 |

첫 번째가 이 슬라이드의 핵심이다. AI가 "목요일 오후 가능합니다"라고 말한 것을 근거로 환자가 목요일을 원했다고 판정하던 문제이며, 그래서 환자 의도 관련 소견은 user turn만 인용하도록 강제한다.

민감정보 경계는 여기에 한 줄로 붙인다. 의미 소견은 하위 Kafka payload와 Langfuse 전송에서 제외되고, `test_main_kafka_payload.py`가 허용 키 집합을 고정해 재귀 검사하며 `test_semantic_layer_boundary.py`가 결정론 계층의 의미 모듈 의존을 정적으로 차단한다. 규칙이 아니라 실행 가능한 계약이라는 점이 요지다.

**S5 · ③ 이걸로 무엇을 하는가, 그리고 한계**

두 운영 화면이 이 챕터의 결과물이다. 하는 일이 서로 다르므로 나란히 놓는다.

## 편집 원칙

- 사실은 `resume/product-engineer.md`를 기준으로 하되, 위키에서 더 정확한 사실이 나오면 **먼저 이력서를 고치고** 산출물에 반영한다.

- 측정하지 않은 절감 시간, 전사 확산률 같은 성과는 주장하지 않는다.
- 특정 회사명과 지원 직무 문구는 포함하지 않는다.
- 도메인 밖 용어는 최초 등장 시 3~4단어로 각주를 단다. 최소한 `DTMF`(전화 키패드 입력), `trunk`(대표번호 회선)는 필요하다.
- ②의 "뭐가 깨졌나"는 각색하지 않고 위키 기록을 근거로 쓴다. 근거가 없으면 그 겹을 비우지 말고 기능 자체를 ②에서 뺀다.
- **②의 기능은 "무엇을 하는가"로 고르지, "어디에 좋은 사건이 있나"로 고르지 않는다.** 흥미로운 버그가 있다는 이유로 사용자에게 의미 없는 내부 구조를 ②에 올리면 챕터가 엔지니어링 일지가 된다. 먼저 이 시스템이 사용자를 위해 무엇을 하는지 나열하고, 그중에서 사건이 붙는 것을 고른다. 순서를 뒤집지 않는다.
- **소유 범위는 역할 라벨과 한 줄로만 적는다.** 어느 기능을 누가 만들었는지 항목별로 쪼개지 않는다. 검증할 수 없고 방어적으로 읽힌다. 팀과 함께한 프로젝트는 "이후 팀이 확장할 수 있는 기반을 만들었다" 정도의 높이를 유지한다.

## 시각 방향

v2의 슬라이드 시스템(16:9, rem 기반 스케일, 다크/라이트)을 유지한다. 구조 변화에 맞춰 두 가지를 더한다.

- **①의 흐름 그림**을 챕터마다 같은 시각 문법으로 그린다. 네 챕터의 ①을 나란히 놓았을 때 같은 종류의 그림으로 보여야 한다.
- **②의 세 겹**을 고정된 시각 패턴으로 표현해, 독자가 세 번째 블록이 항상 실패 사례임을 학습하게 한다.
- **분기 다이어그램 컴포넌트를 새로 만든다.** 기존 `.flow`·`.states`는 일직선이라 갈라지는 구조를 그릴 수 없는데, 챕터 1 S5의 `action_mode` 분기가 이것을 요구한다. 이미지가 아니라 CSS로 만든다 — 덱의 다른 도식이 전부 CSS라 이미지 하나만 섞이면 톤이 어긋나고, 다크·라이트 자동 대응과 텍스트 검색을 잃는다.

- **`AiU`가 두 곳에서 쓰인다.** 회사의 고객용 플랫폼 이름이 AiU인데 현재 챕터 4의 제목도 "AIU 사내 업무지원"이다. 같은 이름이 고객 제품과 사내 도구를 동시에 가리키면 독자가 혼동한다. 챕터 4 재검토 시 이름을 정한다.

챕터 1 구현 후 받은 리뷰에서 다음을 고쳤다.

- **아웃바운드 용도를 사실 기준으로 되돌렸다.** S1 제목의 "놓친 환자에게 먼저 겁니다"는 제품 소개 페이지의 표현을 옮긴 것으로, 사실 기준 문서(`resume/product-engineer.md:74`)가 기록한 "예약 확인·안내 전화"보다 넓고 강한 주장이었다. "예약 확인·안내가 필요한 환자에게"로 바꿨다.
- **"24시간"을 뺐다.** 사실 기준 문서는 병원별 운영시간을 설정으로 제어한다고 기록한다. 24시간 응대는 근거가 없을 뿐 아니라 이 기록과 어긋난다.
- **S2 제목의 관측 범위 혼재를 고쳤다.** "누적 62만 통, 그중 5천 통"은 양방향 누적과 인바운드 4개월 실측을 부분집합처럼 이었다. 인바운드 실측만으로 제목을 다시 썼고 62만은 지표 행에 남겼다.
- **S5 제목을 "예약 신청 접수"로 좁혔다.** 통화 중 커밋이 EMR 확정이 아니라는 챕터의 경계와 제목이 어긋나 있었다.
- **S9 제목의 "예약 성사율"을 "예약 요청 처리 성공률"로 바꿨다.** KPI가 재는 것은 신청·변경·취소·조회 시도의 처리 결과이지 확정된 예약이 아니다.
- **S6의 중의성과 과잉 일반화를 고쳤다.** "의사를 확인합니다"는 병원 맥락에서 醫師로 읽히고, "무엇으로 설정했든 마지막은 메모입니다"는 조건 없이 일반화됐다.
- **S7에 warm 연결률의 귀인 분해를 넣었다.** 17.7%만 두면 시스템 실패율로 오독된다. 미연결 2,386건은 환자 이탈 1,350 · 백엔드 1,011 · 상담원 25다.
- **S3을 둘로 나눴다.** 흐름도·양방향 차이·장애 2건·스택·동시성 상한이 한 장에 있어 1100×620 창에서 텍스트 요소 46개 중 45개가 10px 미만이었다. 구조(S3)와 통화 시작(S4)으로 나눠 24개로 줄였다.
- **S8에서 warm transfer 도식 이미지를 뺐다.** 이미지의 결정 흐름(연결번호 없음 → 메모, 확인 거부 → 메모, cold/warm 분기)이 S6의 분기도와 같은 내용이다. 같은 위키에서 만들었기 때문이다. 이미지는 영문 라벨이고 테마에 반응하지 않으며 작은 창에서 읽히지 않는다. CSS 도식을 남기고 이미지를 뺐다.

**반영하지 않은 것.** 리뷰는 S1에 "직접 소유: 통화 런타임 · 예약 안전 경계 · ..." 한 줄을 넣으라고 제안했다. 넣지 않는다. 편집 원칙이 소유 범위를 항목별로 쪼개지 않기로 정했고, 리뷰 자신도 실제 담당 범위와 일치하는지 확인할 수 없다고 적었다. 확인되지 않은 소유 주장은 역할 라벨보다 약하다.

**글자 크기는 챕터 1의 문제가 아니다.** 루트 스케일이 `clamp(11px, min(1.094vw, 1.944vh), 24px)`이라 창 높이가 620px이면 루트가 12.03px로 줄고 본문이 9.4px가 된다. 1920×1080 전체 화면에서는 16.4px다. 같은 창에서 `about`은 텍스트 요소 78개 중 76개가, `ch2-resolution`은 44개 중 42개가 10px 미만으로 챕터 1의 어느 장표보다 나쁘다. 덱 전체의 성질이며 v2에서 물려받았다. 밀도 분할은 그것대로 가치가 있었지만 이 스케일 문제를 고치지는 못한다.

### 해결됨

- **챗봇 고객상담의 소유 범위를 어디까지 적을 것인가** → 항목별로 적지 않는다. 역할 라벨과 한 줄로만 두며, 어느 채널·기능을 누가 만들었는지는 확정할 수 없고 포트폴리오에 필요하지도 않다. 편집 원칙에 규칙으로 올렸다.

- **AIU의 ② 기능 선별** → 매뉴얼 답변 · 통화 조회와 전환율 · 통화 QA 셋으로 확정했다. 실행 권한을 갖지 않는다는 소유 경계는 ②가 아니라 ①의 정의와 ③의 한계에 둔다.
- **아웃바운드가 인바운드의 분석 파이프라인을 공유하는가** → 별도다. 토픽·테이블·판정 방식이 모두 다르며 성숙도가 한 세대 차이 난다. 이 사실이 관측 챕터의 중심 서사가 됐다. 정보 구조 절 참조.
- **검증 4단계가 아웃바운드에도 적용되는가** → 양방향 공통이다. 챕터 1의 ③에 그대로 넣는다. 단계 명칭의 근거는 `resume/product-engineer.md`이며 위키에는 없다.
- **관측 챕터를 두 파이프라인 비교로 쓸 것인가** → 쓰지 않는다. 비교는 대화분석의 기능이 아니라 해석이었다. 챕터 2는 과정과 용도 두 축으로 전개한다.
- **아웃바운드 신규 예약 경로의 현재 상태** → 레거시 `ScheduleSelectionTask` 경로가 맞다. 위키 기술이 정확하다. 이에 따라 `resume/product-engineer.md`의 아웃바운드 신규 예약 서술에서 인바운드 개념인 "후보 스테이징과 최종 동의" 표현을 제거하고, 실제 동작인 재선택 3회 허용과 스냅샷 교체 기록으로 대체했다(2026-08-25). 챕터 1의 ② 신규 예약은 "같은 문제를 두 번 풀었고 두 번째가 더 나았다"는 서사로 쓴다.

## 완료 기준

- 도메인을 모르는 독자가 각 챕터의 ① 한 장만 보고 그 시스템이 무엇인지 말할 수 있다.
- ②의 모든 슬라이드에 실패 사례 또는 의도적으로 그은 경계가 근거와 함께 들어가 있다. 각색이나 추측이 없다.
- AIU 챕터를 읽고 나면 이 시스템이 무엇을 하고 **무엇을 하지 않기로 했는지** 둘 다 말할 수 있다.
- 인바운드와 아웃바운드가 한 시스템의 두 방향으로 읽히며, 어느 한쪽의 규모나 판단이 묻히지 않는다.
- 관측과 평가 챕터를 읽고 나면 대화분석이 어떤 과정으로 이루어지고 그 결과를 운영자가 어떻게 쓰는지 둘 다 말할 수 있다.
- 모든 챕터가 마지막에 못 하는 것을 명시한다.
- 네 챕터가 같은 3단 리듬을 유지한다. 분량 차이는 ②의 개수에서 발생하며, ①이 2장인 예외는 챕터 1 하나뿐이다.
- 챕터 1의 여덟 줄 한 줄 메시지만 이어 읽어도 챕터 전체가 이해된다. 어느 줄도 슬라이드를 봐야만 뜻이 통하는 상태가 아니다.
- 상담원 연결을 읽고 나면 그것이 예약 기능 위에 얹힌 정책 계층이라는 것, cold와 warm이 무엇을 맞바꾸는지 둘 다 말할 수 있다.
- 키보드·터치 탐색, 다크/라이트 테마, 16:9 및 모바일 뷰포트에서 정상 표시된다.
