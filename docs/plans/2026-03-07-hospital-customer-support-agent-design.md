# Hospital Customer Support Agent 케이스 스터디 설계

## 메타

- 작성일: 2026-03-07
- 타겟: 프로덕트 엔지니어링 전반, AI 엔지니어/백엔드 채용 담당자
- 형식: 마크다운 (한국어)
- 산출물: `case-studies/hospital-customer-support-agent.md`
- 핵심 메시지: 복잡한 병원 문의를 구조적으로 처리할 수 있는 상담 아키텍처를 설계했다

## 문서 목표

- 이력서의 `병원 고객상담 AI Agent 시스템 설계 및 배포` 경험을 독립 케이스 스터디로 확장한다.
- 단순 기능 소개가 아니라 문제 정의와 설계 의사결정을 중심으로 프로젝트를 설명한다.
- LangGraph 기반 상담 흐름 설계, 병원별 지식 조회 구조, 운영 가능한 서비스 경계를 함께 보여준다.
- 역할 범위는 `초기 아키텍처 + 주요 구현`으로 명확히 드러내고, 이후 팀의 Harness·Kakao 확장을 본인 구현처럼 서술하지 않는다.

## 설계 원칙

- 제품 문제와 기술 설계를 함께 보여주는 구조를 사용한다.
- 수치 성과를 과장하지 않고 구조적 난이도와 설계 판단으로 설득한다.
- 구현체 이름이나 세부 코드보다 왜 이런 구조가 필요했는지에 초점을 둔다.
- 기존 케이스 스터디처럼 빠르게 훑을 수 있는 개요를 두되, 본문은 설계 의사결정 중심으로 전개한다.

## 접근 방식

### 추천 접근

- 설계 의사결정 중심형으로 작성한다.
- 문서의 중심 질문은 `복잡한 병원 문의를 처리하려면 무엇을 분리하고 어떤 상태를 가져야 하는가`로 둔다.
- 독자는 제품 문제를 이해한 뒤 핵심 구조와 운영 관점까지 자연스럽게 따라오게 만든다.

### 제외한 접근

- 제품 문제 중심형 단독 접근: 맥락 설명은 쉽지만 기술적 깊이가 약해질 수 있다.
- 아키텍처 중심형 단독 접근: 기술 독자에게는 빠르지만 왜 이런 구조가 필요한지 전달력이 떨어질 수 있다.

## 상위 섹션 구조

### 1. 프로젝트 개요

- 프로젝트 한 줄 소개
- 역할, 기간, 소속
- 무엇을 해결하려는 시스템이었는지 짧게 요약
- 기술 스택은 길게 나열하지 않고 핵심 범주만 정리

### 2. 문제 정의

- 병원 문의는 단순 FAQ가 아니라 기관별 정보 차이와 절차 차이가 있다.
- 상담 도중 개인정보 수집이 필요해도 사용자의 원래 질문 맥락은 유지되어야 한다.
- 실제 서비스가 되려면 답변 생성만이 아니라 지식 데이터, 도구 실행, 운영 구조가 함께 설계되어야 한다.

### 3. 핵심 설계 의사결정

- 일반 상담 흐름과 개인정보 수집 흐름을 분리한 이유
- 병원별 지식 데이터를 검색 기반 응답 구조로 만든 이유
- API, 검색, 대시보드, 배포까지 연결되는 서비스 경계를 초기에 함께 설계한 이유

### 4. 시스템 동작 방식

- 일반 문의 처리 흐름
- 개인정보 수집 후 원래 질문으로 복귀하는 흐름
- 상담원 연결 준비 흐름

### 5. 내가 기여한 부분

- 전체 상담 아키텍처와 상태 전이 구조 설계
- 지식 조회 및 개인정보 수집/복귀 흐름의 핵심 설계 주도
- 운영 가능한 서비스 구조 설계
- 일부 핵심 구간 직접 구현

### 6. 회고 또는 의미

- 상담형 AI 제품에서 상태 관리와 데이터 품질, 운영 구조가 왜 중요한지 정리
- 이 프로젝트가 보여주는 엔지니어링 역량을 짧게 연결

## 핵심 설계 의사결정 상세

### 1. 상담 흐름을 역할별 상태 전이로 분리

- `primary_assistant`, `customer_interaction`, `extract_personal_info`, `tools` 구조를 단순 구성요소가 아니라 역할 분리의 결과로 설명한다.
- 핵심 메시지는 `복잡한 상담일수록 답변 생성보다 상태 제어가 중요하다`로 잡는다.
- 일반 안내, 개인정보 수집, 도구 실행을 한 흐름에 섞지 않고 분리함으로써 상담 품질과 유지보수성을 확보한 점을 강조한다.

현재 런타임은 이 legacy 노드를 역할별 team wrapper로 감싸고 `START → harness_agent`를 추가한다. 포트폴리오에서는 `내가 만든 기반`과 `이후 팀이 확장한 현재 구조`를 시각적으로 분리한다.

### 2. 병원별 지식 조회를 데이터 기반 응답 구조로 설계

- 기관 소개, 운영 시간, 방문 안내, 의료진, 진료/시술, 증명서, 이벤트 등 응답이 병원마다 달라지는 이유를 설명한다.
- 공통 프롬프트만으로는 운영 가능한 품질을 만들기 어렵기 때문에 병원별 데이터 조회 구조가 필요했다는 점을 강조한다.
- 이 프로젝트의 본질을 `FAQ 챗봇`이 아니라 `병원별 데이터에 따라 응답이 달라지는 상담 시스템`으로 정의한다.
- 초기 Qdrant Hybrid Search와 typed knowledge Tool을 기여 범위로 설명하고, 현재 FAQ HTTP/Search source와 Harness 통합은 제품 진화로 구분한다.

### 3. 운영 가능한 서비스 경계를 함께 설계

- 상담 엔진만으로는 서비스가 완성되지 않으며, API 서버, 검색 시스템, 운영 대시보드, 배포 구조가 함께 맞물려야 했다는 점을 설명한다.
- `LangGraph API + FastAPI gateway + PostgreSQL/Redis + 지식 검색 + Docker 배포`를 하나의 제품 구조로 묶어 설명한다.
- 인프라 상세 나열보다 제품 운영 가능성을 만든 구조적 선택이라는 관점으로 쓴다.

### 4. 현재 제품의 Harness 진화

- 모든 실행이 `START → harness_agent`를 통과하고 입력 튜닝 뒤 상담 팀으로 라우팅된다.
- 허용 전이 whitelist, 도구 반복·오류 suspicion, `fast_safe` / `full` controller 모드로 실행 경로를 통제한다.
- 의료 범위 gate, 개인정보·예약 guard, Kakao 버튼·이미지·다국어 응답 같은 채널 정책이 초기 상태 모델 위에 추가됐다.
- 이 기능들은 최신 코드의 중요한 구조지만, Git 기여 이력상 이후 팀의 구현으로 명시한다.

## 표현 가이드

- 섹션마다 `왜 필요했는가 -> 어떻게 설계했는가 -> 무엇이 가능해졌는가` 순서를 유지한다.
- 정량 성과가 없으므로 `정확도`, `가용성` 같은 표현은 근거가 없으면 확정적으로 쓰지 않는다.
- 역할 표현은 `초기 아키텍처 + 주요 구현`을 유지하고, 1인 프로젝트나 최신 Harness 구현자로 보이게 쓰지 않는다.
- LangGraph, Qdrant, FastAPI, PostgreSQL, Redis 등 기술명은 필요한 곳에서만 등장시키고 기술 나열 문서를 피한다.
