# 개발자 이력서 작성 가이드라인

## 1. 이력서의 목적

이력서는 "나는 이런 사람이다"가 아니라 **"나는 이런 결과를 만들어낸 사람이다"**를 증명하는 문서다.
채용 담당자는 이력서를 평균 6-10초 훑어본다. 그 안에 핵심 메시지가 전달되어야 한다.

---

## 2. 문서 구조

아래 순서를 따른다. 채용 담당자가 위에서 아래로 읽을 때 가장 중요한 정보가 먼저 나와야 한다.

| 순서 | 섹션 | 분량 기준 |
|------|------|----------|
| 1 | Header (이름, 연락처, GitHub, LinkedIn, Blog) | 3-4줄 |
| 2 | Professional Summary | 3-4줄 |
| 3 | Core Competencies (기술 스택) | 카테고리별 5-6줄 |
| 4 | Experience (경력, 역순) | 전체의 60-70% |
| 5 | Education | 2-3줄 |
| 6 | Open Source / Side Projects / 기타 활동 | 필요한 만큼 |

---

## 3. 섹션별 작성 원칙

### 3.1 Header

- 이름, 전화번호, 이메일은 필수
- GitHub, LinkedIn, 기술 블로그 링크를 포함한다
- 포트폴리오 사이트가 있으면 추가한다
- 불필요한 개인정보(생년월일, 주소, 사진)는 넣지 않는다

### 3.2 Professional Summary

**핵심 원칙: 열망이 아닌 증거로 쓴다.**

| 나쁜 예 | 좋은 예 |
|---------|---------|
| "AI 기술에 깊은 관심과 열정을 가지고 있습니다" | "LLM 기반 AI Agent를 설계하고 프로덕션에 배포한 경험이 있습니다" |
| "풀스택 개발 경험을 토대로 가능합니다" | "프론트엔드부터 인프라까지 엔드투엔드로 설계하고 운영해왔습니다" |

**포함해야 할 3가지:**
1. **역할 정체성** — 나는 어떤 엔지니어인가 (예: 시니어 풀스택 엔지니어)
2. **핵심 역량** — 가장 강한 기술적 강점 (예: AI 서비스 설계·배포 경험)
3. **차별화 포인트** — 나만의 독특한 조합 (예: 웹 + AI + 인프라를 아우르는 오너십)

**총 경력 연수를 명시**하면 시니어임을 즉시 보여줄 수 있다.

### 3.3 Core Competencies (기술 스택)

- **반드시 카테고리별로 그룹핑**한다
- 한 줄에 모든 기술을 나열하지 않는다
- 공식 표기법을 준수한다 (NextJS → Next.js, Typescript → TypeScript)

**권장 카테고리:**

```
- Frontend: Next.js, React, TypeScript, ...
- Backend: Python, FastAPI, Node.js, ...
- AI / LLM: LangGraph, LangChain, RAG, ...
- Data / Search: PostgreSQL, Qdrant, Redis, ...
- Infra / DevOps: AWS ECS, Docker, Terraform, ...
```

**주의:**
- 실무에서 사용한 기술만 적는다. 튜토리얼만 해본 기술은 넣지 않는다.
- 지원하는 직무와 관련 없는 기술은 과감히 제외한다.

### 3.4 Experience (경력)

이력서에서 가장 중요한 섹션이다. 전체 분량의 60-70%를 차지해야 한다.

#### 3.4.1 기본 구조

```
### 회사명
직책 / 역할
재직기간

#### 프로젝트명 또는 핵심 업무
기간

- [Context] 어떤 제품/문제였는가 (1줄)
- [Action] 내가 구체적으로 한 일 (2-4줄)
- [Result] 측정 가능한 결과 (수치 포함)

기술: 사용한 기술 스택 나열
```

#### 3.4.2 동사 선택

**능동적이고 구체적인 동사**를 사용한다.

| 피해야 할 동사 | 권장 동사 |
|---------------|----------|
| 담당 | 설계했다, 구축했다 |
| 참여 | 구현했다, 개발했다 |
| 수행 | 최적화했다, 개선했다 |
| 지원 | 자동화했다, 통합했다 |
| 경험 | 배포했다, 운영했다 |

#### 3.4.3 성과 표현

**수치가 있으면 반드시 포함한다.**

| 나쁜 예 | 좋은 예 |
|---------|---------|
| "성능을 개선했습니다" | "API 응답 속도를 70% 개선했습니다" |
| "검색 시스템을 구축했습니다" | "하이브리드 검색 시스템을 구축해 검색 정확도를 95% 이상으로 높였습니다" |
| "배포 환경을 구성했습니다" | "Blue/Green 무중단 배포 체계를 구축해 99.9% 가용성을 달성했습니다" |

수치가 없는 경우에도 **규모감**을 전달한다:
- 팀 규모 (예: "15명 규모 프로젝트에서")
- 처리 규모 (예: "일 10만 건 데이터 처리")
- 사용자 규모 (예: "MAU 5,000명 서비스")

#### 3.4.4 시간에 따른 상세도 조절

| 시기 | 상세도 | 기준 |
|------|--------|------|
| 최근 1-2년 | 매우 상세 | 프로젝트별 3-6개 bullet |
| 3-5년 전 | 보통 | 프로젝트별 2-3개 bullet |
| 5년 이상 | 압축 | 회사당 2-3줄로 요약 |

오래된 경험은 과감하게 압축한다. 10년 전 jQuery 경험보다 최근 AI Agent 경험이 훨씬 중요하다.

#### 3.4.5 시니어 개발자의 차별 포인트

시니어라면 단순 구현이 아닌 **의사결정과 설계**를 보여줘야 한다.

- "구현했다" → "설계하고 구현했다"
- "개발했다" → "아키텍처를 설계하고 팀을 리드해 개발했다"
- 기술 선택의 이유, 트레이드오프 판단을 드러낸다
- 엔드투엔드 오너십(기획→설계→구현→배포→운영)을 강조한다

### 3.5 Education

- 학교명, 전공, 졸업연도만 간결하게 적는다
- 경력이 5년 이상이면 학력은 크게 중요하지 않다
- 비전공자라면 별도로 언급하지 않아도 된다 — 경력이 말해준다

### 3.6 Open Source / Side Projects / 기타 활동

**지원 직무를 강화하는 항목만 선별**한다.

강하게 어필되는 항목:
- 유명 오픈소스 프로젝트 기여 (Contributor/Maintainer)
- 기술 커뮤니티 발표
- 기술 블로그 운영 (꾸준한 포스팅)
- 관련 분야 사이드 프로젝트

약하거나 제외해도 되는 항목:
- 10년 이상 된 자격증/수료
- 직무와 무관한 연수/활동
- 단순 수료 이력

## 4. ATS(Applicant Tracking System) 대응

많은 회사가 이력서를 자동으로 스크리닝하는 ATS를 사용한다.

### 4.1 ATS 통과를 위한 체크리스트

- [ ] 표준 섹션 제목 사용 (Experience, Education, Skills)
- [ ] 기술명은 공식 표기법 사용 (Next.js, TypeScript, PostgreSQL)
- [ ] 특수한 표나 이미지 사용 최소화
- [ ] 링크는 텍스트로 표시
- [ ] 직무 공고의 핵심 키워드를 자연스럽게 포함
- [ ] PDF 변환 시 텍스트 선택 가능한 형태 유지

### 4.2 키워드 전략

지원하는 직무 공고를 분석하고, 공고에 나온 기술명과 역할 키워드를 이력서에 자연스럽게 녹인다. 단, 키워드를 억지로 나열하지 않고 경험 설명 안에 포함시킨다.

## 5. 포맷과 가독성

### 5.1 분량

| 경력 | 권장 분량 |
|------|----------|
| 주니어 (1-3년) | 1페이지 |
| 미드레벨 (3-7년) | 1-2페이지 |
| 시니어 (7년 이상) | 2-3페이지 |

3페이지를 넘기지 않는다.

### 5.2 가독성 원칙

- bullet point를 사용한다 (긴 문단 X)
- 한 bullet은 1-2줄을 넘기지 않는다
- 일관된 날짜 형식을 사용한다 (예: 2024.03 - 2024.08)
- 볼드체는 핵심 키워드에만 제한적으로 사용한다
- 여백을 충분히 확보한다 — 빽빽한 이력서는 읽히지 않는다

### 5.3 일관성

- 기술명 표기: 문서 전체에서 동일하게 (Next.js를 NextJS와 혼용하지 않는다)
- 문체: "~했습니다"로 통일하거나 "~함"으로 통일한다. 섞지 않는다
- 날짜 형식: "2024.03"이면 전부 이 형식으로 통일한다

## 6. 최종 점검 체크리스트

이력서를 완성한 후 아래 항목을 확인한다.

- [ ] 6초 안에 "이 사람이 뭘 하는 사람인지" 파악할 수 있는가?
- [ ] Summary에 열망이 아닌 증거가 담겨 있는가?
- [ ] 기술 스택이 카테고리별로 정리되어 있는가?
- [ ] 각 경험 항목에 구체적 동사 + 수치 기반 성과가 있는가?
- [ ] 최근 경험이 가장 상세하고, 과거로 갈수록 압축되어 있는가?
- [ ] 지원 직무와 무관한 내용이 제거되었는가?
- [ ] 기술명 표기와 문체가 문서 전체에서 일관적인가?
- [ ] 분량이 2-3페이지를 넘기지 않는가?
- [ ] 오탈자가 없는가?
- [ ] PDF로 변환했을 때 깨지는 부분이 없는가?
